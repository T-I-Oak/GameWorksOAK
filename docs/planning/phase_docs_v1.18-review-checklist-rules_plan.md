# レビュー確認項目の明文化計画

## 開発スコープ

- レビュー担当が `docs/common/99.compliance_checklist.md` を使用し、各項目の適用可否と該当項目への準拠を確認する義務を共通ルールへ明記する。
- レビュー報告に確認結果・根拠・適用外の理由を記録する方法を定める。
- ファイル・フォルダーの用途と保存期間から命名の妥当性を確認し、接頭辞のない一時成果物の不要な永続化をレビュー対象に含める。
- マージ・push 時の確認項目は実行後に確認し、承認草案の時点で未実施の項目を確認済みとして扱わないことを明記する。

## 対象文書

- `docs/common/03.workflow_guide.md`: レビュー時のチェックリスト使用と成果物の命名確認を規定する。
- `docs/common/03.phase_workflow.md`: 確認担当・確認時期・確認内容・結果の記録先、要修正時の実装への差し戻しを具体化する。
- `docs/common/04.common_structure.md`: 用途と保存期間に応じた命名基準とレビュー報告の記録内容を整合させる。
- `docs/common/99.compliance_checklist.md`: チェックリスト使用・結果記録・命名妥当性・不要な永続化の確認項目を追加する。

## 対象外

- ゲーム・ポータルの機能変更。
- 既存ファイル全体の整理・削除。
- ツール固有スキルの変更。

## 完了条件

- レビュー担当が共通チェックリストの各項目の適用可否を判断し、該当項目を確認する手順が明記されている。
- 確認結果・根拠・適用外の理由の記録先がレビュー報告として明確である。
- 新規・変更ファイルとフォルダーは、名称だけでなく用途・保存期間・マージ後の継続利用の必要性を確認する。
- 開発期間だけ必要な成果物は `dev_`、即座に削除可能な成果物は `tmp_`、規定のフェーズ成果物は `phase_` として扱い、既存の `local_` の用途と管理方法も維持する。
- 接頭辞のない作業メモ・検証結果・中間生成物なども内容から判定し、不適切な命名や不要な永続化は修正指摘とする。
- 継続利用が必要な仕様書・テスト・保守用スクリプトは、用途を確認して永続成果物として扱える。
- 承認草案時点の確認結果と、承認後のマージ・push 時に確認する項目が区別され、未実施を確認済みと扱わない。
- 対象文書の規定が一致し、既存の承認・差し戻し・削除・マージ・push の順序を維持する。
- 全テストと本番ビルドを実行し、結果と失敗時の調査を実装報告へ記録する。

## バージョンとブランチ

- 予定バージョン: `1.18.0`。
- ブランチ: `docs/v1.18-review-checklist-rules`。
- 計画では設定を更新せず、初回実装開始時に `package.json` と `package-lock.json` を更新する。
- 文書変更に対する利用者向け更新履歴の記載要否は、共通構成の規定に従って実装時に確認する。

## 実装・検証方針

- 命名基準を共通構成、実施手順をフェーズ作業手順に置き、関連文書とチェックリストを整合させる。
- 共通チェックリスト自体をプロジェクトごとに書き換える運用にはせず、個別の確認結果はレビュー報告に残す。
- 接頭辞による削除走査だけでは検出できない命名漏れを、レビュー時の用途・保存期間の確認で検出する。
- 文書の参照先、責務、承認前後の確認時期、既存規定との整合性を確認する。
- 文書のみの変更として実装を模倣するテストは追加せず、`npm test` と `npm run build` を実行する。
- オーナー判断が必要な点が実装中に生じた場合は、共通手順に従って提示し、判断を記録する。
