# ゲーム開発ライフサイクルの手順整備計画

## 開発スコープ

共通規約に分散している情報を、ゲームの開始から公開までの順序で参照できるようにする。
作業者が理解する規約と、実際に実施する構築・公開作業を分ける。

- 対象リポジトリ: GameWorksOAK（ポータル・共通部）。
- 合意したブランチ: `docs/v1.12-game-lifecycle`。
- 予定バージョン: `1.12.0`。初回実装フェーズ開始時に設定を更新する。
- `docs/common/` に次の4文書を追加する。番号付きファイル名とし、既存文書との並びを確認して決める。
    - ゲーム開発全体の流れ。
    - 新規ゲームの環境構築手順。
    - 公開準備手順。
    - ゲーム公開手順。
- 既存の共通規約に入口となる参照を追加し、共通構成・準拠チェックリスト等の適用時期を必要な範囲で整理する。

## 記載する内容

### ゲーム開発全体の流れ

環境構築、設計・開発開始、オーナーによる公開判定、公開準備と予告公開、公開に向けた開発継続、ゲーム公開を示す。
公開判定は設計・開発期間中の任意のタイミングで行う。
公開しないと判断した場合には開発を終了する場合があることを示す。
公開時期を確定するための判断事情や、予告期間の長さは規定しない。
各作業手順への入口を設け、個々の開発タスクのフェーズ運用とは区別する。

### 新規ゲームの環境構築手順

公開を前提とせず、ローカルで開発・テスト・本番ビルドができ、Gitで管理できる状態を到達点とする。
リポジトリ、共通側との隣接配置、実行環境と依存関係、標準フォルダ、Vite、実行コマンド、共通ライブラリ接続、Git除外、テスト、公開処理を伴わないCIを整理する。
ポータル登録、紹介素材、GitHub Pages、デプロイ設定は環境構築の実施項目に含めない。
作業者が読むべき規約は実施チェック項目から分けて案内する。

### 公開準備手順

オーナーの公開判定後に行う作業を整理する。
公開環境・デプロイ設定、予告に使うゲーム紹介・公開予定情報・素材、標準JSON、ポータル登録、予告公開と確認、ゲーム公開までに必要な確認を扱う。
紹介情報はゲーム側の公開URLから取得されるため、予告用データの公開とゲーム本体の公開を分ける方法を、既存構成に照らして確認する。
ポータルのボタンを無効にすることだけでゲームURLへの直接アクセスを制限できるとは扱わない。
既存構成で成立しない部分や未決定の運用は、決定事項と区別してオーナーへ報告する。

### ゲーム公開手順

公開対象の版、検証結果、共通ライブラリの公開状態を確認し、既存のマージ・push規約に従ってデプロイする手順を示す。
公開先の動作確認、ポータルの予告から公開中への切替と表示確認、バージョン・更新履歴の扱いを既存規約へ接続する。
Major更新はオーナーの明示指示が必要であり、手順だけを根拠に自動更新しない。

## 対象外

- ゲーム・ポータル・共通ライブラリの機能変更。
- 実際の新ゲーム環境構築、ポータル登録、予告公開、デプロイ。
- 公開判定の具体的な時期、予告期間の数値化。
- 公開方法を成立させるための新機能実装や、未合意の運用の確定。
- 共通規約全体の再編、今回の目的に関係しない修正。

機能変更が必要と判明した場合は本件に混ぜず報告する。
スコープ・予定バージョン・ブランチ名を変更する場合は再合意を得る。

## 完了条件

- 4文書が存在し、全体の流れから各手順へ辿れる。
- 環境構築作業と、作業者が理解する規約が分かれている。
- 環境構築は公開を前提とせず、ポータル登録・公開環境設定を含まない。
- オーナーの公開判定、非公開判断時の分岐、予告公開、ゲーム公開の順序が明確である。
- 各手順に実施項目・完了条件・詳細規約への参照がある。
- 既存規約を重複定義せず、共通構成・チェックリストとの適用時期に矛盾がない。
- 予告用情報とゲーム本体の公開の分離について、既存構成で確認できる内容と未決定事項が区別されている。
- 文書間リンク、全テスト、本番ビルドの確認結果が実装報告に記録されている。

## 実装・テスト方針

- 共通構成、ワークフロー、フェーズ作業手順、共通ライブラリ公開運用、ポータル仕様と実装、既存ゲームのCIを照合する。
- 既存ゲームの個別設定を共通必須事項として無条件に転記しない。
- 共通規約の詳細は正本へリンクし、新文書では順序・実施項目・完了条件を中心に記述する。
- 実装開始時に `package.json` と `package-lock.json` を `1.12.0` に更新する。
- 文書内の相対リンク・参照先、手順の順序、適用時期、既存規約との整合を確認する。
- ソース機能変更を伴わないため、文書をなぞるだけのテストは追加しない。
- 実装終了草案前に共通側で `npm.cmd test` と `npm.cmd run build` を実行し、コマンドと結果を実装報告へ記録する。
- 失敗時は原因を調査し、今回の範囲・変更が原因なら修正・再実行し、既存または範囲外なら理由を記録する。
- 本件は利用者向けの機能変更を伴わない文書整備として、更新履歴の扱いを共通規約に照らして判断する。
