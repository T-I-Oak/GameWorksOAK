# 正式版・仮版の共通公開

## 公開先と起動条件

| 操作 | 公開先 | gh-pages 配置先 |
| --- | --- | --- |
| master への push | https://t-i-oak.github.io/{Repository}/ | ルート |
| 開発ブランチの workflow_dispatch | https://t-i-oak.github.io/{Repository}/preview/ | preview/ |

手動実行時は Actions の Deploy to GitHub Pages から開発ブランチを選ぶ。
master の手動実行、タグ、その他のイベントは配置前に失敗させる。
公開先の入力欄は設けず、共通処理がイベント・ref・リポジトリ名から決める。
仮版は全開発ブランチで共有する1枠で、最後に成功した実行で上書きする。
仮版も公開URLであり、認証や非公開を保証しない。

## 呼び出し設定

各ゲームの `.github/workflows/deploy.yml` は次を使用する。

```yaml
name: Deploy to GitHub Pages
on:
  push:
    branches: [master]
  workflow_dispatch:
permissions:
  contents: write
jobs:
  publish:
    uses: T-I-Oak/GameWorksOAK/.github/workflows/publish.yml@master
```

共通仕様の修正を各ゲームへ届けるため参照は公開済み master とする。
再現確認では Actions 実行に記録された共通ワークフローと共通 checkout のコミットIDを記録する。
共通変更は先に GameWorksOAK のレビュー・マージ・push を完了してから使う。
共通ワークフローの更新は共通部で行い、インターフェース変更時はゲーム側の移行バックログを用意する。
ポータルは同一コミットの `./.github/workflows/publish.yml` を呼び、ソース・補助スクリプトも自リポジトリを使う。

## ビルドの契約

- Node.js 24、`npm ci`、`npm run build` を使用し、成果物を `dist/` へ出力する。
- 共通処理が `DEPLOY_BASE_PATH` を渡す。Vite の `base` はこの値を採用する。
  ローカルの既定値は各リポジトリの正式版パスにできる。
- 例: `base: process.env.DEPLOY_BASE_PATH || '/NewGame/'`。
- 呼び出し元は `app/`、共通部の公開済み master は隣の `GameWorksOAK/` に checkout する。
  ゲームの相対importはこの隣接配置を使用する。
- ポータルは `app/` 内の自身のライブラリを使う。
- 共通スクリプトがビルド後の index.html のアセット参照と公開パスを照合する。
  dist直下の preview は予約領域で、ビルド成果物に含めない。

## 配置と保持

同一リポジトリの正式版と仮版は共通 concurrency group で直列化する。
実行中の公開を新しい要求でキャンセルしない。GitHub の同時実行制御では保留中の要求が置き換わる場合がある。
正式版の清掃では preview を除外し、仮版は target-folder を preview に限定する。
古いハッシュ付き素材は公開対象の範囲で清掃する。
公開用ブランチは gh-pages、Pages の公開元はそのルートに設定する。
force push は使用しない。

## 公開結果の確認

Actions の対象コミット・共通部 checkout・転送先・成功を確認する。
正式版と仮版を順に公開し、他方の index.html と素材が保持されることを確認する。
公開URLを直接開いて読み込み・素材・バージョンを確認する。
ポータル自身の配置先と、`?preview=on` によるゲーム参照先は独立している。
各ゲームの移行時は標準JSON・画像・ロゴ・プレイ先・更新履歴を仮版から取得できることも確認する。
ローカルテストだけで Actions や公開URLの確認を完了扱いにしない。
