# Common Workflow Guide - GameWorks OAK

## 1. バージョン管理
セマンティックバージョニング（Major.Minor.Patch）に基づき、プロジェクトの状態を管理します。

- Major: オーナーから明示的な指示があった場合にのみ 1 加える。大規模な刷新、またはアーキテクチャの根本的な変更であっても、担当者判断では更新しない。
- Minor: 新規開発を開始する時に 1 加える（例: 0.16.x -> 0.17.0）。
    - `docs/planning/backlog.md` の `要望・バグ指摘` セクションから新しいタスクを選んで開発を始める場合は、新規開発として扱う。
    - 実機テストや公開環境での確認のために merge / push した後、`docs/planning/backlog.md` の `オーナー検証` セクションに残っている同一タスクへのフィードバックを修正する場合は、同じ Minor の継続開発として扱う。
    - 継続開発では Minor を更新しない。これにより、実機検証中の微調整で公開履歴に意味の薄い改版が積み重なることを防ぐ。
- Patch: ソースコードの変更を伴うコミット、独立した作業単位（タスク）の完了、または意味のある修正・変更ごとに 1 加える（例: 0.17.0 -> 0.17.1）。
    - 実機テスト後のフィードバック修正であっても、ソースコードを変更する場合は Patch を更新する。
    - ドキュメント修正のみの場合は更新不要とする。
    - テスト時に公開物とソースの一致を確認できるよう、パッチ更新の際は package.json 等のプロジェクト設定も同時に更新すること。
    - 公開用の更新履歴（update_history.json）およびブランチ名においては、Patch を省略した Minor 単位（x.y 形式）を使用する。

バージョン判定の例:

- `要望・バグ指摘` にある「チュートリアル対象を自動スクロールする」に着手する: 新規開発として `1.6.x -> 1.7.0`。
- `1.7.0` を実機テストのために merge / push し、同じタスクを `オーナー検証` へ移動する。
- オーナー検証で「スクロールは smooth の方がよい」とフィードバックがあったため修正する: 継続開発として Minor は `1.7` のまま、ソース修正があるため `1.7.0 -> 1.7.1`。
- オーナーから OK が出たため `オーナー検証` から削除する。その後、別の `要望・バグ指摘` に着手する: 新規開発として `1.7.x -> 1.8.0`。

## 2. バックログ運用
`docs/planning/backlog.md` は、新規開発か継続開発かを判定できるよう、以下のセクションで管理します。

- 要望・バグ指摘: これから対応する新しい要望、改善案、不具合指摘を記載する。
- オーナー検証: 実装済みで、オーナーによる実機テストや公開環境確認を待つタスクを記載する。

開発開始時の判定は以下です。

- `オーナー検証` に残っているタスクへのフィードバック対応: 継続開発。Minor は更新せず、ソース修正があれば Patch を更新する。
- `オーナー検証` に対象タスクがなく、`要望・バグ指摘` から新しいタスクを取り出す対応: 新規開発。Minor を更新する。

要望やバグ指摘に対応したら、そのタスクを `オーナー検証` へ移動します。
オーナーから OK が出たタスクは、適切なタイミングで `オーナー検証` から削除します。
完了済みタスクを残し続けることは、継続開発と新規開発の判定を曖昧にするため避けてください。

## 3. ブランチ戦略
すべての開発は作業用のブランチで行い、直接 `master` ブランチへの変更は行いません。

- メインブランチ: `master`
    - GameWorks OAK プロジェクトの正系ブランチは `master` です。
    - **GitHub のデフォルト設定等により `main` ブランチが作成されることがありますが、原則として使用せず、すべてのマージ先を `master` に指定してください。**
- 命名規則: [prefix]/v[Major].[Minor]-[description]
    - 例: feature/v0.17-new-ui, fix/v0.17-bug-fix
- 開発完了時の処理: 開発ブランチが `master` にマージされる際、そのブランチ内で作成された dev_ プレフィックスのファイルはすべて削除してください。
- アトミック・コミットの徹底: 可能な限り 1 ファイル修正ごとに個別のコミットを行い、変更履歴を明確に保つこと。
- コマンド実行の安全性: Windows（PowerShell 等）環境でのエラー防止のため、&& による連続実行を避け、コマンドは一つずつ実行すること。
- 承認ゲートの設置: 実装計画（Implementation Plan）の各ステップにおいて、適宜オーナーの確認・承認を得ながら進めること。

## 4. 開発完了チェックリスト
マージおよびオーナーへの完了報告を行う前に、以下の項目をすべて満たしている必要があります。

- 仕様との整合性: docs/ 配下の仕様書と実装が乖離していないこと。
- テストの合格: `npm test` を実行し、全件が合格していること。
- 更新履歴の更新: 必要に応じて public/data/update_history.json を更新すること。
- 一時ファイルの削除: `dev_` および `tmp_` ファイルが削除されていること。
- バックログの整理: 実装済みタスクは `オーナー検証` へ移動し、オーナー OK 済みのタスクは削除すること。
- コミット後の状態確認: `git status --short --branch` を確認し、意図しない `M` が残っていないこと。
    - 改行コードのみの差分であっても、公開物とソースの一致確認を妨げるため放置しないこと。


## 5. テスト方針
デグレードを未然に防ぐため、以下の 2 つの視点でテストを実施します。

- 仕様テスト (tests/spec/): 仕様書に記述された挙動が正しく実装されているかを検証する。
- 実装テスト (tests/implementation/): モジュール内部のロジックやデータ整合性を検証するユニットテスト。
- TDD（テスト駆動開発）の原則適用:
    - 複雑なロジック（計算処理、状態管理、イベント連鎖等）を伴う実装においては、原則として TDD 形式（実装前にテストを作成する手法）を必須とする。
    - 実装前にテストコードで仕様を定義することで、設計の妥当性を保証し、デグレードを未然に防ぐ。
