# Common Workflow Guide - GameWorks OAK

## 1. バージョン管理
セマンティックバージョニング（Major.Minor.Patch）に基づき、コードの状態を明示します。

- Major: 大規模な刷新、またはユーザーの指示があった場合のみ。
- Minor: 新しい開発ブランチを開始する際に 1 加える（例: 0.16.x -> 0.17.0）。
- Patch: 開発中、コードを改修して検証（テスト依頼）を行うタイミングで 1 加える。

## 2. ブランチ戦略
すべての開発は作業用のブランチで行い、直接メインブランチへの変更は行いません。

- 命名規則: [prefix]/v[Major].[Minor]-[description]
    - 例: feature/v0.17-new-ui, fix/v0.17-bug-fix
- 開発完了時の処理: 開発ブランチがメインブランチにマージされる際、そのブランチ内で作成された `dev_` プレフィックスのファイルはすべて削除してください。

## 3. 開発完了チェックリスト
マージおよびユーザーへの完了報告を行う前に、以下の項目をすべて満たしている必要があります。

- 仕様との整合性: docs/ 配下の仕様書と実装が乖離していないこと。
- テストの合格: `npm test` を実行し、全件が合格していること。
- 改版履歴の更新: 必要に応じて public/data/update_history.json を更新すること。
- 一時ファイルの削除: `dev_` および `tmp_` ファイルが削除されていること。
- バックログの更新: 完了したタスクのステータスを更新すること。

## 4. テスト方針
デグレードを未然に防ぐため、以下の 2 つの視点でテストを実施します。

- 仕様テスト (tests/spec/): 仕様書に記述された挙動が正しく実装されているかを検証する。
- 実装テスト (tests/implementation/): モジュール内部のロジックやデータ整合性を検証するユニットテスト。
