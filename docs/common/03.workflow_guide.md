# Common Workflow Guide - GameWorks OAK

## 1. バージョン管理

- Majorはオーナーから明示指示があった場合だけ1加える。大規模刷新でも担当者判断では更新しない。
- 新規開発はMinorを1上げる。同一タスクのフィードバック対応は、マージ・公開後でも元のMinorを維持する。
- バージョン設定（package.json・package-lock.json等）は初回の実装開始時に、計画で決めたMinor・Patch 0へ更新する。
- 再実装・レビュー差し戻し・オーナーフィードバック対応で実装を再開するときはPatchを1上げる。
- 実装終了草案が承認されず変更に着手するときもPatchを1上げる。同じ修正版の個々の指摘・コミットでは上げず、再提示草案が再び差し戻されたら次の修正着手時にもう1上げる。
- 計画・レビュー・マージへの移行だけでは更新しない。文書・設定だけの実装も対象とする。
- 確認依頼のバージョンは設定・各プロジェクトの確認画面と一致させる。
- 利用者向けupdate_history.jsonはMinor単位（x.y）で管理する。v1以降の運用とし、v0期間は空配列を維持する。記載対象と形式は[共通構成](04.common_structure.md)に従う。

## 2. バックログ運用

docs/planning/backlog.mdに以下の欄を設ける。

- 「要望・バグ指摘」: 新規開発の全体作業計画の唯一の台帳。新規要望・スコープ外指摘を依存関係と優先順に記載する。
- 「オーナー検証」: 実装済みの結果について、オーナーが「現時点で確認しない」と判断した項目だけを記録する。レビューでの確認指定も含む。未回答や実装済みという理由で一律移動しない。

同一タスクへのフィードバックは継続開発、新しい要望・バグ指摘への着手は新規開発とする。却下・確認済みは同じ項目がバックログにあれば削除する。検証ID・判断・追加時のチャット通知は[フェーズ作業手順](03.phase_workflow.md)に従う。

## 3. ブランチ・フェーズ・コミット

すべての開発は作業ブランチで行い、masterを直接変更しない。正系とマージ先はmasterとし、mainを使用しない。

- 命名は[prefix]/v[Major].[Minor]-[description]。Patchを含めない。例: docs/v1.11-phase-rules。
- スコープ・対象外・完了条件・予定バージョン・ブランチ名を提案し、明示合意後に合意した名前で作成する。変更には再合意を得る。担当ツールの既定値を理由に名前を変えない。
- 計画・実装・レビュー・マージの判定、開始合意、終了草案承認、引継ぎ書、コミットは[フェーズ作業手順](03.phase_workflow.md)に従う。
- フェーズ終了時に変更一式と承認済み成果物をコミットし、1ファイルごとの個別コミットは必須としない。
- Windowsでのエラー防止のため、コマンドは一つずつ実行し、&&による連続実行を避ける。

## 4. 検証と完了条件

対象テストは随時実行し、実装終了草案前に全テストと本番ビルドを実行する。文書・設定のみでも省略しない。各コマンド・結果は実装報告に記録する。失敗は草案前に調査し、今回の範囲・変更が原因なら修正・再実行する。既存・明らかな範囲外なら調査結果と今回修正しない理由を記録する。要求仕様とテストの矛盾はオーナーへ確認し、都合よくテストを変更しない。

レビューは仕様・計画・差分・報告・検証判断を照合し、ソースを変更しない。要修正なら実装へ戻す。未解決指摘なしはレビュー実施担当だけが記録する。

マージ前に全フォルダーのdev_・tmp_・phase_を安全に削除・再走査し、追跡済み削除をコミットする。マージ開始指示にはmasterへのマージとgit push origin masterを含み、追加承認は求めない。push後はgit rev-parse masterとgit ls-remote origin refs/heads/masterのID一致を確認する。失敗時はローカルのマージを保持して調査し、force pushせず、反映未確認を完了扱いしない。詳細は[フェーズ作業手順](03.phase_workflow.md)、ゲーム担当の共通側確認は[公開運用](90.common_library.md#公開状態の確認)に従う。

## 5. テスト方針
デグレードを未然に防ぐため、以下の 2 つの視点でテストを実施します。

- 仕様テスト (tests/spec/): 仕様書に記述された挙動が正しく実装されているかを検証する。
- 実装テスト (tests/implementation/): モジュール内部のロジックやデータ整合性を検証するユニットテスト。
- TDD（テスト駆動開発）の原則適用:
    - 複雑なロジック（計算処理、状態管理、イベント連鎖等）を伴う実装においては、原則として TDD 形式（実装前にテストを作成する手法）を必須とする。
    - 実装前にテストコードで仕様を定義することで、設計の妥当性を保証し、デグレードを未然に防ぐ。

## オーナー検証中の指摘

オーナー検証中や利用者による操作確認中に受けた指摘は、現在の開発スコープと照合する。

- 現在の作業範囲内であれば、そのブランチで修正する。
- 現在の作業範囲外であれば、`backlog.md` の未完了項目として依存関係と優先順に合う位置へ追加する。
- オーナーが修正を指示したブロッキングバグだけは、現在のスコープ外でもその修正を行う。バックログへ送って止めない。バグの報告やバックログへの追加だけでは修正しない。

スコープ外の新規作業を「オーナー検証」へ記録してはならない。「オーナー検証」は、開発ブランチで実装済みの結果について、オーナーが確認するための項目だけを置く。

開発中に、別のオーナー検証が進むことがある。4つの判断は、その開発と非同期に届く。バックログへの反映は、届いた時点で行う。

- 「現時点で確認しない」の項目は、「オーナー検証」へ追加する。実装はしない。
- 「項目却下」「項目確認済み」の項目は、「オーナー検証」から外す。実装はしない。
- 「項目でフィードバックあり」は内容を記録する。修正が必要な場合は、現在のスコープ内なら実装で対応し、スコープ外なら「要望・バグ指摘」へ依存関係と優先順に合う位置で記録する。
- 差し戻しの実装は、現在の開発スコープと照合する。範囲内ならそのブランチで修正する。範囲外なら、修正の指示があるまで実装しない。ブロッキングバグは、修正を指示されたときだけ直ちに修正する。
- 差し戻しの着手は、その項目をマージした Minor の継続開発である。Minor は上げない。Patchの更新は「実装フェーズのバージョン更新」に従い、差し戻し対応の実装フェーズ開始時に行う。コミットのたびにPatchは上げない。

## 定期見直し

新規開発で Minor の下1桁が 0 になるとき（10回ごと）、その版は文書とソースの見直しだけにする。機能の実装と同じブランチへ混ぜない。同じ Minor の Patch では始めない。周期と範囲は本共通規定に従う。

- 開発ルール: 共通ルールとプロジェクト固有の規定を読み直し、着手するフェーズを確認する。
- 文書: 現在存在しない仕様、章構成、参照先を確認する。文書の分割は共通の文書ガイドに従う。
- テスト: 文書の挙動とテスト対象を照合する。ソースを分割・移動した場合は、テストの責務と配置の対応も見直す。
- ソース: 未使用コード、文書との整合性、ファイルサイズを点検する。コーディング基準は共通のコーディングガイドに従う。
- バックログ: オーナー検証が利用者が操作・確認できる単位で1件ずつ判定できることと、要望・バグ指摘の依存関係・優先順を確認する。
- 点検範囲と修正内容、全テスト・本番ビルドの結果を実装報告とチャットへ記録する。

見直しブランチでは新規機能や仕様変更を混ぜない。発見した不具合が見直し範囲に入らない場合は、要望・バグ指摘へ記録する。
