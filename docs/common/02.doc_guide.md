# Common Document Guide - GameWorks OAK

## 1. 原則：明快なドキュメント
「正しいドキュメント」とは、情報が正確であること以上に、「読者が正しく理解できること」を指します。

- 簡潔さの維持: 1つのドキュメントは100～300行程度に収めるように努めてください。
- 適切な分割: 内容が肥大化する場合は、無理に1ファイルにまとめず、意味の区切りでファイルを分割してください。
- 可読性優先: 長文による説明を避け、構造化された記述（見出し、箇条書き等）を用いて、一目で構成が理解できるようにします。
- 命名による順序の明示: 複数のドキュメントが存在する場合、ファイル名の先頭に番号（例: 01.name.md）を付与し、読者が読み進めるべき順序を明示してください。

## 2. 役割：成果報告の場ではない
ドキュメントは、作成者や編集者の功績を誇示するための場所ではありません。

- 不要な装飾の排除: 自分が編集した箇所を太字にするなどの、自己アピール目的の装飾は一切行わないでください。ドキュメントをノイズのない読みやすい状態に保つことが目的です。
- 必然性の追求: 装飾（太字、斜体、色等）を用いるのは、読者の理解を助けるために客観的な必然性がある場合のみに限定します。
    - 補足: ファイル名、ディレクトリ、ソースコード上のシンボル、コマンド等をバッククォートで括る（インラインコード）記述は、情報の種類を明確にし可読性を高めるための適切な装飾として許容・推奨されます。

## 3. 内容：最新の「意味」への集中
ドキュメントは常にプロジェクトの「最新の状態」と「その意図」を示すものであるべきです。

- 履歴管理の分離: 過去の経緯や変更点は GitHub の履歴（コミットログやプルリクエスト）で管理します。ドキュメント内に過去との比較や変更の履歴を残さないでください。
- 「なぜ」の記述: 「前版より〇〇を変更した」「v1.2のバグに対応した」といった過去との比較ではなく、「なぜ現在の設計になっているのか」という意味と意図を記述してください。
- 例外: ユーザー向けに提供する `update_history.json` は、リリース情報としての役割があるため、この原則の対象外とします。
