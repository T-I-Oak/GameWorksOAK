# フェーズ作業手順

[共通ワークフローガイド](03.workflow_guide.md)と合わせて適用する。成果物の構成・追跡は[共通構成](04.common_structure.md#フェーズ成果物)を参照する。

### 実装フェーズのバージョン更新

バージョン設定（`package.json`、`package-lock.json`）は実装フェーズで更新する。以下のルールを適用する。

- 初回の実装フェーズ開始時は、計画で決めたMinorを使用し、Patchを0にする。
- 2回目以降の実装フェーズ開始時は、Minorを維持してPatchを1上げる。レビュー指摘やオーナー検証のフィードバックによる実装への差し戻しも含む。
- 実装フェーズの終了が承認されず、実装を変更する場合も、変更に着手するときにPatchを1上げる。同じ実装フェーズ内でも適用する。
- 同じ修正版を作る途中の個々の指摘やコミットごとにはPatchを上げない。再提示した終了草案が再び承認されず、さらに実装を変更する場合は、もう1上げる。
- レビューやマージへの移行だけではバージョンを更新しない。確認を依頼するときは、更新済みの設定・画面表示と一致するバージョンをチャットに記載する。

### 担当範囲

各担当は依頼されたプロジェクトとフェーズの責務に従う。ゲーム担当にとってGameWorksOAKは共通ルール・ライブラリの参照専用であり、問題と必要な変更はオーナーへ報告して共通部担当へ依頼する。共通部担当自身によるGameWorksOAKの更新には、この参照専用制限を適用しない。

### フェーズ開始の指示

AI の担当は固定しない。オーナーは、正式指示「フェーズを開始してください」または短縮指示「フェーズ開始」により、新しいフェーズの開始を依頼する。両指示は、現在ブランチと保存済みの引継ぎ書から判定したフェーズを開始する指示である。引継ぎ書の「次に開始するフェーズ」は開始対象そのものを示す。

オーナーは、同じ AI へ連続するフェーズを依頼してもよいし、フェーズごとに別の AI へ依頼してもよい。原則として、各フェーズは新しいセッションで開始する。AI は、依頼されたフェーズに定められた責務を越えて作業してはならない。

### フェーズの共通ステップ

マージ以外の各フェーズは、必ず次の4ステップを順に行う。

1. **フェーズ確認**: 現在ブランチと `phase_handover.md` の有無・「次に開始するフェーズ」を確認し、表に従って今回のフェーズを一意に判定する。状態を特定できない場合は、推測せずオーナーへ判断を依頼する。
2. **フェーズ宣言**: 判定したフェーズ名をチャットで宣言して停止する。オーナーの合意を得る前に主作業を始めない。
3. **実施**: そのフェーズの主作業と成果物作成を行う。この時点では `phase_handover.md` を更新しない。
4. **承認**: 次フェーズへ向けた `phase_handover.md` の草案をチャットへ表示して停止する。草案を表示した時点ではフェーズは完了しておらず、保存済みの引継ぎ書も更新しない。草案表示後のオーナーの `ok` は、その草案の承認を表す。承認されたときだけ、表示した草案と同じ内容を `phase_handover.md` へ書き込み、下記の「フェーズ終了時のコミット」を行う。コミット成功と保存内容を確認した後に「フェーズが完了しました」と記載し、コミットIDと保存した引継ぎ書の内容をそのまま示す。

マージ・フェーズは承認ステップを持たない。masterへのマージとpush後に、操作後に確認したマージ結果・push結果と `phase_handover.md` を削除した事実を報告する。削除済みまたは過去の成果物を現在の状態として報告してはならない。

### 計画フェーズの進め方

計画フェーズでは、共通ステップの「実施」を以下の順序で進める。

1. バックログ、要求・仕様、現在の実装、関連する共通ルールを確認し、今回の開発内容を提案する。提案には、開発スコープ、対象外、完了条件、予定バージョン、作成するブランチ名を含める。バックログの大項目全体を自動的に今回のスコープとせず、依存関係と優先順を踏まえて範囲を示す。
2. 提案に対するオーナーの明示的な合意を待つ。修正を求められた場合は提案を更新して再提示する。合意を得るまでブランチを作成しない。
3. 合意した名前でブランチを作成し、現在のブランチ名が合意した名前と一致することを確認して報告する。
4. 合意内容に基づき、開発スコープ、対象外、完了条件、実装・テスト方針を計画書へ記載する。スコープ、予定バージョン、ブランチ名を変更する必要が生じた場合は、変更案を提示し、オーナーの再合意を得てから反映する。
5. 次フェーズを「実装」とする引継ぎ書の草案を提示し、共通ステップの「承認」へ進む。承認後に引継ぎ書を保存し、計画書などとともに終了コミットを行う。

計画フェーズ開始への合意、開発内容への合意、計画フェーズの終了承認は、それぞれ別の判断である。フェーズ開始への合意は、開発内容やブランチ作成への合意を兼ねない。開発内容への合意は、終了承認を兼ねない。各合意・承認は、直前に提示した提案または草案に対するものとして扱い、調査への指示や提案への質問を合意と解釈しない。

### ブランチの命名と合意

- ブランチ名は、[共通ワークフローガイド](03.workflow_guide.md)の命名規約 `[prefix]/v[Major].[Minor]-[description]` に従う。
- 接頭辞は作業内容に応じて選び、予定バージョンのMajor・Minorを使用する。Patchは含めない。例えば、新規機能は `feature/v0.44-result-screen`、同じMinorの不具合修正は `fix/v0.43-mobile-controls` とする。
- ブランチ名は開発内容とともに提案し、オーナーの明示的な合意後に、その名前で作成する。
- 担当者や使用ツールの既定値を理由に、接頭辞を追加したり、合意した名前を変更したりしない。各ツールの設定は、この規定に従えるように調整する。

### フェーズ終了時のコミット

各フェーズの終了時に、ソース・アセット・設定・通常の文書と `phase_` 成果物への変更をコミットする。次担当が直前フェーズの状態へ戻せるよう、これらを未コミットのまま次フェーズへ引き継がない。`phase_` はignoreせずGitで追跡する。`dev_` と `tmp_` は既存のignore運用を維持する。

- 計画・実装・レビューでは、引継ぎ書の草案承認後、承認内容を保存してからコミットする。差し戻しを決めたレビューも対象とする。草案の提示だけでは終了コミットを行わない。
- 変更したソース・アセット・設定・通常の文書、そのフェーズの `phase_` 成果物および承認済み `phase_handover.md` を含める。`dev_`・`tmp_`、無関係な変更や一時検証ファイルは含めない。対象ファイルを明示して通常の `git add` で追加し、ignore対象を強制追加しない。
- コミットメッセージには、フェーズ名と対象ブランチの開発内容が分かる記述を入れる。
- コミット前にステージ済み差分を確認し、コミット後に `git log -1` と `git status --short --branch` で保存結果を確認する。フェーズの追跡対象ファイルに未コミット差分が残っている場合やコミットに失敗した場合は、完了と報告せず、原因を解消する。無関係な差分が残る場合は、その内容を報告する。コミット対象の変更がない場合は、空コミットを作らず、その事実と現在のHEADのコミットIDを報告する。
- マージでは、下記の削除規定に従って `dev_`・`tmp_`・`phase_` を削除する。追跡済み `phase_` 成果物の削除と残る追跡対象の変更をコミットしてからmasterへマージする。
- 計画・実装・レビューの終了コミットはローカルへの記録とする。マージ・フェーズではmasterへのマージに続けてpushを行う。過去の終了時点を推測してコミットを分割したり、履歴を書き換えたりしない。

### マージ後のpush

- masterへのマージが成功したら、同じマージ・フェーズ内で `git push origin master` を実行する。マージ開始の指示は、このpushも含むものとし、追加の承認は求めない。
- ゲーム担当はマージ着手前とpush直前に、[共通ライブラリの公開運用](90.common_library.md#公開状態の確認)に従って公開状態を確認する。共通部担当自身のリポジトリ更新にはゲーム担当向けの参照専用制限を適用しない。
- push成功後、`git rev-parse master` と `git ls-remote origin refs/heads/master` のコミットIDが一致することを確認する。
- pushが失敗した場合は、ローカルのマージ結果を保持し、原因を調査する。force pushは行わない。リモートへの反映が確認できるまでは、マージ・フェーズが完了したと報告しない。解消できない場合は、マージ済み・push未完了の状態と原因を報告する。


### ブランチ内の一時成果物

開発ブランチでは、`docs/planning/` に次の `phase_` ファイルを置く。`<branch>` はブランチ名をファイル名として安全な表記へ置換した識別子とする。

- `phase_<branch>_plan.md`: 開発スコープ、対象外、完了条件、実装・テスト方針。
- `phase_<branch>_implementation.md`: 計画に対する実装結果、変更箇所、対象テスト・全テスト・本番ビルドの結果、失敗時の調査結果、提示したオーナー検証項目・判断・フィードバック対応・保留理由。
- `phase_<branch>_review.md`: 現時点のレビュー結果。未解決指摘の有無を明確に記載する。
- `phase_handover.md`: 次に開始するフェーズと、次担当へ伝えるべき注意事項を記録する唯一の引継ぎ書。

これらは開発期間中だけ維持する `phase_` 成果物であり、ignoreせず各フェーズ終了時にコミットし、マージ前に削除する。生存期間は従来の `dev_` 成果物と同じである。フェーズを表す記述は `phase_handover.md` だけに置き、計画書・実装報告・レビュー報告へ状態フィールドを重複して持たせない。

### マージ前の中間成果物・一時ファイルの削除

マージ前に、このリポジトリのすべてのフォルダーを確認し、名前が `dev_`・`tmp_`・`phase_` で始まるファイルおよびフォルダーをすべて削除する。`docs/planning/` だけに限定しない。追跡済み・未追跡・ignore対象のすべてを対象とし、ignore対象を通常のGit差分に表示されないという理由で残してはならない。

- 削除前に対象一覧と絶対パスを確認し、対象がこのリポジトリ内に収まることを検証する。別リポジトリのGameWorksOAKやGit管理領域（`.git`）は対象に含めない。
- 追跡済み成果物の削除はコミットに含める。過去の成果物はGit履歴に残り、masterの現在のファイルには残さない。
- 削除後、ignore対象も含めて全フォルダーを再確認し、3接頭辞のファイル・フォルダーが残っていないことを確認してからmasterへマージする。
- この規定の導入時は、既存の開発計画・実装報告・レビュー報告・引継ぎ書を `dev_` から `phase_` へ移行し、参照も更新する。引継ぎ書は `phase_handover.md` だけを正本とし、旧名を残さない。

### `phase_handover.md` の記載と更新

`phase_handover.md` には、少なくとも次の3項目を置く。

- 次に開始するフェーズ
- 直前のフェーズで完了したこと
- 次担当への注意事項（なければ「なし」）

計画フェーズは、開発ブランチと計画書を作成し、承認された後に `phase_handover.md` へ次フェーズ「実装」を記録する。以後、各非マージフェーズは承認された草案だけを `phase_handover.md` に更新する。マージ・フェーズは、すべての `phase_` 成果物とともに `phase_handover.md` を削除する。

### フェーズの判定と成果物

| ブランチと引継ぎ書の状態 | 実行するフェーズ | 実施してよいこと | 出力して停止するもの |
| --- | --- | --- | --- |
| `master` 上で `phase_handover.md` がない | 計画 | 開発内容・予定バージョン・ブランチ名を提案し、オーナーの明示的な合意後に、合意した名前で開発ブランチを作成して計画書を作成する。 | 引継ぎ書の草案 |
| 開発ブランチ上で `phase_handover.md` があり、「実装」と記載されている | 実装 | 計画の範囲内で設計・実装、対象テスト・全テスト・本番ビルド、必要な仕様書・バックログ更新を行う。必要なオーナー検証を提示し、判断・フィードバックを反映する。レビュー指摘への修正もこのフェーズで行う。 | `phase_<branch>_implementation.md` と引継ぎ書の草案 |
| 開発ブランチ上で `phase_handover.md` があり、「レビュー」と記載されている | レビュー | 計画、設計、仕様、共通ルール、ブランチ差分、テスト結果、オーナー検証の判断と対応を照合する。修正後の再確認もこのフェーズで行う。ソースは変更しない。オーナーが指定した保留項目の確認を扱う。 | `phase_<branch>_review.md` と引継ぎ書の草案 |
| 開発ブランチ上で `phase_handover.md` があり、「マージ」と記載されている | マージ | 必要な確認が完了していることを確認し、全フォルダーから `dev_`・`tmp_`・`phase_` を削除してコミット・masterへのマージ・origin/masterへのpushを行う。 | masterへのマージ結果・push結果 |

`master` 上に `phase_handover.md` がある、開発ブランチ上に `phase_handover.md` がない、引継ぎ書のフェーズが上表にない、またはブランチ自体を特定できない場合は異常状態である。AIはフェーズを推測して開始せず、オーナーへ判断を依頼する。

### 完了時に記載する次フェーズ

| 完了したフェーズ | `phase_handover.md` に記載する次フェーズ |
| --- | --- |
| 計画 | 実装 |
| 実装 | レビュー |
| レビュー | 未解決指摘または修正が必要なオーナーフィードバックがあれば実装。それらがなく、検証項目の判断・対応・明示的な保留が記録されていればマージ。 |
| マージ | `phase_handover.md` を削除するため、次フェーズは記載しない。 |

レビュー報告に未解決指摘がないことは、レビューを実施した AI だけが記録できる。実装フェーズの AI は、レビュー指摘またはオーナー検証のフィードバックへの対応内容を実装報告へ追記する。

フェーズ判定に `git status` の未コミット差分の有無を使ってはならない。計画書自体も差分になるためである。`git diff master...HEAD` はレビュー対象の確認に使うが、着手するフェーズは `phase_handover.md` の記載だけで判定する。

### 実装フェーズの完了条件

実装中は、変更した機能に対応する対象テストを随時実行する。対象テストの成功だけで実装フェーズを完了してはならない。

必要なオーナー検証項目は実装中に提示し、各項目の判断を得て記録する。修正が必要なフィードバックは実装中に対応し、再確認する。未回答の項目や未対応のフィードバックを、担当者の判断でレビューへ持ち越して終了草案を提示しない。保留できるのは、オーナーが「現時点で確認しない」と判断した項目だけとする。

フェーズの承認草案を表示する前に、テストスイート全体と本番ビルドを実行する。ソース、アセット、文書、設定だけの変更であっても省略しない。実装報告には、対象テスト、全テスト、本番ビルドのそれぞれについて、実行したコマンドと結果を記録する。

全テストまたは本番ビルドが失敗した場合、実装担当は承認草案を表示する前に原因を調査する。今回の計画範囲または今回の変更が原因なら修正して再実行する。既存の失敗または明らかなスコープ外の失敗なら、失敗内容、調査結果、今回修正しない理由を実装報告へ記録する。テストが要求仕様と矛盾すると判断した場合は、テストを都合よく変更せず、オーナーへ確認を求める。

レビュー担当は、実装報告に記載された検証結果とブランチ差分を照合する。レビューのためにテストを再実行してもよいが、実装の完了根拠を記録する責務は実装担当にある。

### 実装中のオーナー検証項目の扱い

オーナーによる判断が必要な項目は、確認可能な実装ができた時点でチャットに提示する。レビューまで一律に持ち越さない。

提示する項目は、各プロジェクトの利用者が操作・確認できる単位で1件ずつ判断できるものとする。各項目に一意のIDを必ず付与し、確認が必要な理由、操作手順、期待する結果、確認バージョンを示す。同じ項目は判断・フィードバック・対応記録・再提示・バックログでも同じIDを使用し、対象を明確にする。確認バージョンは設定（`package.json` 等）と各プロジェクトの確認画面の表示に一致させる。具体的な表示位置は各プロジェクトで定める。バックログの各項目にはバージョンを書かない。

オーナーは項目ごとに次の4つの判断を行う。判断と対応結果は実装報告に記録する。

- **項目却下**: 検証対象から除外する。確認済みや不具合と解釈しない。バックログに同じ項目があれば削除する。
- **項目確認済み**: 検証を完了する。バックログに同じ項目があれば削除する。
- **項目でフィードバックあり**: 内容を確認し、現在のスコープ内の修正は実装中に行う。修正後に結果を再提示し、判断を得る。フィードバックがあるだけで一律に不合格とは扱わない。
- **現時点で確認しない**: その項目だけを `backlog.md` の「オーナー検証」へ記録する。レビューで確認する場合もこの判断に含む。未回答を保留と解釈しない。

「オーナー検証」へ追加する際は、項目のID・確認内容・追加理由をチャットで明示する。別開発の判断を非同期に反映する場合も同じとし、ファイル更新だけで済ませない。この通知はオーナーによる保留判断を代替しない。

レビュー担当は記録済みの判断と対応結果を照合し、却下・確認済みの項目を再依頼しない。オーナーがレビューで確認すると指定した保留項目は、その指定に従って扱う。レビュー中に新たな必要項目が見つかった場合は、その理由を示して提示し、同じ4つの判断を受ける。修正が必要になった場合は実装へ戻す。

オーナー検証の回答を待つ間も、保存済みの引継ぎ書は現在のフェーズのままとする。独立した「オーナー検証」フェーズは設けない。
