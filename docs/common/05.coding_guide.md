# Common Coding Guide - GameWorks OAK

## 1. 開発の 7 つの設計原理
持続可能なコード品質を維持するため、以下の 7 つの原理を実装の基準とします。

- 単純性 (Simplicity): 複雑さを最小限に抑える。1ファイル 500行制限を遵守し、常に最も単純な解決策を選択する。同じ目的の処理を個別にコーディングせず、共通化を徹底する。
- 同型性 (Isomorphism): 似た役割のものは同じ形にする。命名、構造、スタイルに一貫性を持たせ、直感的な理解を助ける。
- 対称性 (Symmetry): 概念の対になる部分は実装も対称にする（追加と削除、表示と非表示など）。
- 階層性 (Hierarchy): 抽象化のレベルを整理する。基盤、構造、装飾、文脈などのレイヤーを明確に分離する。
- 線形性 (Linearity): 関係を単純な直線にする。副作用を排除し、1つの変更が広範囲に波及するスパゲッティ状態を避ける。
- 明晰性 (Explicitness): 意図を明確にする。マジックナンバーを排除し、不透明な解決策（!important 等）を避ける。
- 安全性 (Safety): 不具合を最速で顕在化させる。

## 2. 安全性（Safety）の詳細
開発時における安全性とは、「バグを隠さず顕在化させること」と、「外界の不確実性（環境エラー）からユーザーを適切に保護すること」を明確に区別し、その両面を実装することを指します。

- 不具合（バグ）の自然な顕在化: 開発上の論理ミスや設計不備に対して過剰なチェック（if 文の乱立）を行わず、表示の崩れやエラーとして自然に顕在化させることを許容する。
- 防御的プログラミングの禁止: 「念のため」の try-catch や null チェック、デフォルト値へのフォールバックなど、バグを隠蔽し得る実装を排除する。不具合を隠して「動いているふり」をさせることは、将来の致命的なデグレードを招く不安全な行為である。
- 外界（環境）エラーの適切な処理: API取得失敗、アセットの404、オフライン状態などの外的要因によるエラーは「バグ」とは見なさず、適切にユーザー体験（UX）を保護すること。Loadingのままフリーズさせるなど、ユーザーを「立ち往生」させる実装は避け、フォールバック（失敗UIや代替表示）と復帰手段を提供すること。

## 3. 意味論（Semantics）
コードが「何をしたいか（What）」を明確に示すため、実装とコメントを適切に使い分けます。

- 宣言的な実装: 直接的な演算や手続き（How）をそのまま並べるのではなく、意味のある単位で抽象化（定数化・メソッド化）する。これにより、コードを「意図の宣言」として読める状態にする。
- 無意味なコメントの排除: 実装手順（How）をコメントに書くことは冗長であり、避けるべきである。コメントは、コードから読み取ることが難しい背景や選択の理由（Why）に限定する。
- 仕様への集約: 「何をするものか（What）」の詳細は原則として仕様書（docs/spec.md等）に記述し、コードやコメントに過度な依存をさせない。

## 4. 統一（Unity）
重複は技術的負債の源泉です。同じ目的の処理は必ず共通化（メソッド化）し、情報の唯一の正解（Single Source of Truth）を定義してください。
