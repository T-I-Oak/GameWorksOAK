# 新規ゲームの環境構築手順

## 到達点

公開を前提とせず、ローカルで開発・テスト・本番ビルドができ、Gitで管理できる状態を作る。
前後の流れは[ゲーム開発全体の流れ](08.game_lifecycle.md)を参照する。

## 作業前に理解する規約

以下は作業者が読む規約であり、公開設定を実施するチェック項目ではない。

- [開発理念](01.philosophy.md)と[文書ガイド](02.doc_guide.md)。
- [ワークフロー](03.workflow_guide.md)と[フェーズ作業手順](03.phase_workflow.md)。バージョン、ブランチ、承認、コミットの規則を確認する。
- [共通構成](04.common_structure.md)と[共通ライブラリ](90.common_library.md)。標準構成とローカル参照の仕組みを確認する。
- [コーディング](05.coding_guide.md)、[CSS](06.css_design_rules.md)、[モバイル対応](07.mobile_browser_rules.md)。実装時から適用する。

## 実施項目

### 事前配置ファイルの確認と保全

オーナーがゲームで使用するファイルを、環境構築前に対象フォルダーへ格納している場合がある。
リポジトリ作成・雛形生成・依存導入などを始める前に、未追跡・ignore対象を含む既存ファイルとフォルダー、その内容・用途を確認する。

- 既存ファイルを保持して不足分を追加する。雛形の一括展開やフォルダーの初期化で、既存ファイルを上書き・削除しない。
- 同名ファイルや配置の競合がある場合は差分と用途を確認する。事前配置ファイルの変更・移動・置換が必要なら、対象と理由をオーナーへ示し、合意後に行う。用途が分からないファイルを不要と判断しない。
- ビルドや初期化コマンドが消去・再生成する出力先も確認し、事前配置ファイルが含まれる場合は、保全方法を決めてから実行する。Git管理外のファイルはGitから復元できると扱わない。
- 作業前の一覧と内容を比較できるよう、必要に応じてバックアップやハッシュを記録する。作業後に、合意した変更以外の欠落・内容変更がないことを確認する。

### 構築作業

1. ゲーム用のGitリポジトリを用意し、`master`を正系とする。実際の開発ブランチは計画フェーズの合意後に作成する。
2. ゲームと共通部を隣接配置する。例は以下のとおり。共通部の取得元は`T-I-Oak/GameWorksOAK`とし、ゲーム担当は参照先を編集しない。

   ```text
   workspace/
     GameWorksOAK/
     NewGame/
   ```

3. Node.jsとnpmを用意し、採用するVite・テストツールが要求する実行環境を確認する。既存ゲームの依存関係をそのまま必須とはせず、ゲーム側の`package.json`に必要な依存を明示し、ロックファイルを管理する。
4. [標準フォルダー構成](04.common_structure.md#1-標準フォルダー構成)に従い、`docs/`、`src/`、`public/`、`scripts/`、`tests/`とルートの`index.html`を整える。バックログには「要望・バグ指摘」「オーナー検証」を設ける。公開用JSONや紹介素材の作成は公開準備で行う。
5. Viteを設定し、入口・出力先・ローカル参照先を確認する。開発時点で必要な`base`を使い、公開URLに対応する値は公開準備で確認する。バージョンは設定から取得し、ゲームの確認画面に表示する。
6. `package.json`に開発・テスト・本番ビルドの実行コマンドを定義する。標準の呼出しは`npm.cmd run dev`、`npm.cmd test`、`npm.cmd run build`とし、プレビューには必要に応じて`npm.cmd run preview`を用意する。
7. 共通機能は隣接する`GameWorksOAK/src/lib/`から相対importする。階層数はimport元に合わせる。Viteとテスト環境の両方で参照が解決されることを確認する。導入例は[共通ライブラリ](90.common_library.md)を参照する。
8. `.gitignore`に依存・出力・一時ファイルを登録する。`node_modules/`、`dist/`、`local_*`、`dev_*`、`tmp_*`などを対象とし、`phase_*`は除外しない。秘密情報や個人用設定もコミットしない。
9. 仕様テスト・実装テストの配置と実行環境を設定し、入口や共通機能接続を実際に確認できるテストを用意する。複雑なロジックのTDDは[テスト方針](03.workflow_guide.md#5-テスト方針)に従う。
10. CIを用意する場合は、依存導入・テスト・ビルドまでとする。共通部を別途checkoutし、相対importが解決する隣接位置へ配置またはリンクする。Pagesへの転送や公開ブランチへの書込みは含めない。

コマンドはゲームのリポジトリ直下で一つずつ実行する。ロックファイルがある再現環境では`npm.cmd ci`で依存を導入し、依存の初期設定・変更時には`npm.cmd install`でロックファイルを更新する。

## 完了条件

- 事前配置ファイルが保持され、合意した変更以外の欠落・内容変更がない。
- ローカルで起動でき、テストと本番ビルドが成功する。
- ゲームから共通ライブラリを参照でき、必要なコードがビルドに取り込まれる。
- 構成・コマンド・実行環境がゲーム側の文書で確認できる。
- Gitの追跡対象と除外対象が適切である。CIを設けた場合は公開処理を伴わずに成功する。

この時点ではポータル登録、紹介素材、GitHub Pages、デプロイ設定を完了条件にしない。
設計・開発を進め、オーナーの公開判定後に[公開準備](10.game_release_preparation.md)へ進む。
