# 共通仕様準拠チェックリスト (Compliance Checklist) - GameWorks OAK

各プロジェクトの開発完了時やセルフレビュー時に、本チェックリストを用いて共通仕様への準拠状況を確認してください。

## 1. ドキュメントガイド ([02.doc_guide.md](02.doc_guide.md))
- [ ] 各ドキュメントが 100〜300 行程度に収まっているか
- [ ] 内容に応じて適切にファイルを分割しているか
- [ ] 構造化（見出し、箇条書き等）が適切に行われ、可読性が保たれているか
- [ ] ファイル名の先頭に番号（例: `01.name.md`）が付与されているか
- [ ] ファイル名によって読者が読み進めるべき順序が明確か
- [ ] 自己アピール目的の不要な装飾（編集箇所の太字化など）が排除されているか
- [ ] 過去の経緯や変更履歴ではなく、「なぜ現在の設計になっているのか」という意図が記述されているか

## 2. プロジェクト構造・ファイル配置 ([03.common_structure.md](03.common_structure.md))
- [ ] `docs/planning/backlog.md` が存在し、タスクが管理されているか
- [ ] `public/assets/` に画像等のリソースが配置されているか
- [ ] `public/data/` に JSON データファイルが配置されているか
- [ ] `index.html` がルート直下に配置されているか
- [ ] `local_` プレフィックスのファイルが適切に Git 管理外（.gitignore）となっているか
- [ ] `dev_` プレフィックスのファイルが適切に Git 管理外（.gitignore）となっているか
- [ ] `tmp_` プレフィックスのファイルが適切に Git 管理外（.gitignore）となっているか
- [ ] `public/data/project_info.json` が定義されているか
- [ ] `logo.path` は正しい相対パスか（例: `assets/logo.svg`）
- [ ] `button.type` は現在の公開状態（`published` / `pending`）と一致しているか
- [ ] `public/data/update_history.json` に今回の変更内容が追記されているか
- [ ] 更新履歴が降順（新しい順）で記載されているか
- [ ] バージョン表記が Minor 単位（x.y 形式）か
- [ ] ユーザー体験（UX）に関わる内容が具体的に記載されているか
- [ ] 更新履歴に内部改善に関する過剰な記述はないか
- [ ] `public/assets/logo.svg` が配置されているか

## 3. スタイルガイド ([04.style_guide.md](04.style_guide.md))
- [ ] `!important` を使用していないか
- [ ] HTMLへの直接的なインラインスタイル記述を避けているか
- [ ] スタイルが CSS ファイルで管理されているか（動的計算が必要な場合を除く）
- [ ] クラス命名規則が意味に基づいているか
    - [ ] テーマ: `.theme-*`
    - [ ] 機能: `.UpperCamelCase`
    - [ ] 質感: `.texture-*`
    - [ ] 状態: `.state-*`
    - [ ] 種別: `.lower-case`

## 4. コーディングガイド ([05.coding_guide.md](05.coding_guide.md))
- [ ] **設計の 7 つの原理が遵守されているか**
    - [ ] **単純性 (Simplicity)**
        - [ ] 1ファイル 500行制限を遵守しているか
        - [ ] 同じ目的の処理を個別に書かず、共通化を徹底しているか
        - [ ] 常に最も単純な解決策を選択しているか
    - [ ] **同型性 (Isomorphism)**
        - [ ] 似た役割のものが同じ形（命名・構造・スタイル）をしているか
    - [ ] **対称性 (Symmetry)**
        - [ ] 追加/削除、表示/非表示など、対になる概念の実装が対称か
    - [ ] **階層性 (Hierarchy)**
        - [ ] 基盤・構造・装飾・文脈などの抽象化レベルが整理されているか
        - [ ] 異なるレイヤーが明確に分離されているか
    - [ ] **線形性 (Linearity)**
        - [ ] 副作用が排除されているか
        - [ ] 1つの変更の影響が予測可能な範囲（直線的）に留まっているか
    - [ ] **明晰性 (Explicitness)**
        - [ ] 定数化・メソッド化により意図が宣言的に示されているか
        - [ ] マジックナンバーが排除されているか
        - [ ] 不透明な解決策が排除されているか
    - [ ] **安全性 (Safety)**
        - [ ] 「念のため」のガードを排しているか（本質的に不確定な場合を除く）
        - [ ] 不具合（バグ）を隠蔽せず、顕在化させているか
- [ ] **環境エラーへの対応**
    - [ ] 外界（環境）エラーに対して Loading 放置になっていないか
    - [ ] 適切な復帰手段や代替表示を提供しているか

## 5. ワークフロー ([06.workflow_guide.md](06.workflow_guide.md))
- [ ] 開発開始前に `dev_implementation_plan.md` を作成したか
- [ ] 計画書についてオーナーの承認を得たか
- [ ] 1タスク 1パッチ（Patch バージョンアップ）の原則を守っているか
- [ ] 開発完了後、`dev_` で始まる一時ドキュメントを削除したか
- [ ] `backlog.md` から、今回完了したタスクを削除したか



## 6. 共通ライブラリ ([07.common_library.md](07.common_library.md))
- [ ] 共通ライブラリを直接参照しているか
- [ ] ライブラリで提供されている機能の独自重複実装を避けているか
