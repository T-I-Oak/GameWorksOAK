# 共通仕様準拠チェックリスト (Compliance Checklist) - GameWorks OAK

各プロジェクトの開発完了時やセルフレビュー時に、本チェックリストを用いて共通仕様への準拠状況を確認してください。

## 1. ドキュメントガイド ([02.doc_guide.md](02.doc_guide.md))
- [ ] 各ドキュメントが 100〜300 行程度に収まっているか
- [ ] 内容に応じて適切にファイルを分割しているか
- [ ] 構造化（見出し、箇条書き等）が適切に行われ、可読性が保たれているか
- [ ] ファイル名の先頭に番号（例: `01.name.md`）が付与されているか
- [ ] ファイル名によって読者が読み進めるべき順序が明確か
- [ ] 自己アピール目的の不要な装飾（編集箇所の太字化など）が排除されているか
- [ ] 過去の経緯や変更履歴ではなく、「なぜ現在の設計になっているのか」という意図が記述されているか

## 2. ワークフロー ([03.workflow_guide.md](03.workflow_guide.md)、[フェーズ作業手順](03.phase_workflow.md))

- [ ] 現在ブランチと保存済み引継ぎ書でフェーズを判定し、異常状態を推測で進めていないか
- [ ] 非マージフェーズで宣言・開始合意・主作業・終了草案承認の順序を守ったか
- [ ] スコープ・対象外・完了条件・予定バージョン・ブランチ名への明示合意後に、合意したブランチを作成したか。変更には再合意を得たか
- [ ] 開始合意・開発内容合意・終了草案承認を区別し、質問や調査指示を合意扱いしていないか
- [ ] Majorの明示指示、新規開発のMinor更新、同一タスクのMinor維持を守ったか
- [ ] 初回実装開始で計画Minor・Patch 0、再実装や終了草案差し戻しの修正着手でPatch +1としたか。個々のコミットでは更新していないか
- [ ] 文書・設定だけの実装もバージョン・全テスト・本番ビルドの対象にしたか
- [ ] 検証を実装中に1件ずつ、一意のID・理由・操作・期待結果・設定と画面に一致する確認バージョンで提示し、同じIDで判断・対応・再提示・バックログを追跡したか
- [ ] 却下・確認済みを対象とバックログから外し、フィードバックを範囲と照合して対応したか
- [ ] オーナー検証には明示保留だけを残し、追加時にID・確認内容・理由をチャットで示したか。非同期判断も同様に反映したか
- [ ] 未回答を保留扱いせず、必要な判断・対応前に終了草案や引継ぎ書を進めていないか
- [ ] スコープ外の要望・指摘は唯一の全体作業台帳「要望・バグ指摘」に依存関係・優先順で記録し、ブロッキングバグは修正指示がある場合だけ直ちに対応したか
- [ ] 対象テスト・全テスト・本番ビルドのコマンドと結果、失敗調査と修正しない理由を実装報告へ記録したか。仕様とテストの矛盾を確認したか
- [ ] レビューが計画・仕様・差分・検証判断を照合し、ソースを変更せず、要修正なら実装へ戻したか
- [ ] 未解決指摘なしはレビュー実施担当だけが記録したか
- [ ] 承認済み草案と同じ引継ぎ書を保存し、変更一式を明示した通常のgit addでコミットしたか。強制追加や無関係な差分を含めていないか
- [ ] コミット前にステージ差分、後にgit log -1とgit status --short --branchを確認したか。失敗・追跡対象の残差分を完了扱いしていないか
- [ ] 変更なしは空コミットを作らずHEADを報告し、過去の終了コミットの推測分割・履歴改変を避けたか
- [ ] 非マージ終了後はコミットIDと保存引継ぎ書全文を報告したか
- [ ] マージ前に全フォルダーのdev_・tmp_・phase_を安全確認して削除・再走査し、追跡済み削除をコミットしたか
- [ ] masterへのマージとpushを追加承認なしで行い、ローカルmasterとremote masterのID一致を確認したか。失敗時は保持・調査しforce pushを避けたか
- [ ] マージ完了時に確認結果と引継ぎ書削除を報告したか。反映未確認を完了扱いしていないか
- [ ] 新規Minor末尾0の版を文書・ソースの見直し専用とし、機能・新仕様を混ぜず、点検範囲・修正・全テスト・ビルド結果を報告したか

## 3. プロジェクト構造・ファイル配置 ([04.common_structure.md](04.common_structure.md))
- [ ] `docs/planning/backlog.md` が存在し、タスクが管理されているか
- [ ] `public/assets/` に画像等のリソースが配置されているか
- [ ] `public/data/` に JSON データファイルが配置されているか
- [ ] `index.html` がルート直下に配置されているか
- [ ] `local_` プレフィックスのファイルが適切に Git 管理外（.gitignore）となっているか
- [ ] `dev_` プレフィックスのファイルが適切に Git 管理外（.gitignore）となっているか
- [ ] `tmp_` プレフィックスのファイルが適切に Git 管理外（.gitignore）となっているか
- [ ] `phase_` 成果物はignoreせず追跡し、フェーズ状態を引継ぎ書以外へ重複記載せず、既存dev_成果物の移行と参照更新・旧引継ぎ書削除を行ったか
- [ ] `public/data/project_info.json` が定義されているか
- [ ] `logo.path` は正しい相対パスか（例: `assets/logo.svg`）
- [ ] `logo.path` の参照先は許可形式（SVG / PNG / JPEG / WebP）のロゴ画像か
- [ ] `button.type` は現在の公開状態（`published` / `pending`）と一致しているか
- [ ] v0.x.x 期間の `public/data/update_history.json` は空配列 `[]` になっているか
- [ ] v1 リリース以降の `public/data/update_history.json` に今回の変更内容が追記されているか
    - [ ] 更新履歴が降順（新しい順）で記載されているか
    - [ ] バージョン表記が Minor 単位（x.y 形式）か
    - [ ] ユーザー体験（UX）に関わる内容が具体的に記載されているか
    - [ ] 記載禁止事項（リファクタリング、テスト追加等の内部作業名）が含まれていないか
    - [ ] 「内部改善」と記載する場合、詳細な理由や作業内容が併記されていないか
- [ ] `logo.path` で指定したロゴ画像が配置されているか

## 4. コーディングガイド ([05.coding_guide.md](05.coding_guide.md))
- [ ] **設計の 7 つの原理が遵守されているか**
    - [ ] **単純性 (Simplicity)**
        - [ ] 1ファイル 500行制限を遵守しているか
        - [ ] 同じ目的の処理を個別に書かず、共通化を徹底しているか
        - [ ] 常に最も単純な解決策を選択しているか
    - [ ] **同型性 (Isomorphism)**
        - [ ] 似た役割のものが同じ形（命名・構造・スタイル）をしているか
    - [ ] **対称性 (Symmetry)**
        - [ ] 追加/削除、表示/非表示など、対になる概念の実装が対称か
    - [ ] **階層性 (Hierarchy)**
        - [ ] 基盤・構造・装飾・文脈などの抽象化レベルが整理されているか
        - [ ] 異なるレイヤーが明確に分離されているか
    - [ ] **線形性 (Linearity)**
        - [ ] 副作用が排除されているか
        - [ ] 1つの変更の影響が予測可能な範囲（直線的）に留まっているか
        - [ ] 拡縮する機能は関連機能への影響を管理し、座標・寸法を扱う機能は対象や祖先要素の拡縮を考慮しているか（新規追加・変更時も確認する）
    - [ ] **明晰性 (Explicitness)**
        - [ ] 定数化・メソッド化により意図が宣言的に示されているか
        - [ ] マジックナンバーが排除されているか
        - [ ] 不透明な解決策が排除されているか
        - [ ] 拡縮の適用範囲・倍率の管理責務・座標系と変換方法が明確で、必要な座標変換が共通化されているか
    - [ ] **安全性 (Safety)**
        - [ ] 「念のため」のガードを排しているか（本質的に不確定な場合を除く）
        - [ ] 不具合（バグ）を隠蔽せず、顕在化させているか
- [ ] **環境エラーへの対応**
    - [ ] 外界（環境）エラーに対して Loading 放置になっていないか
    - [ ] 適切な復帰手段や代替表示を提供しているか

## 5. CSS設計ルール ([06.css_design_rules.md](06.css_design_rules.md))
- [ ] `!important` を使用していないか
- [ ] HTMLへの直接的なインラインスタイル記述を避けているか
- [ ] スタイルが CSS ファイルで管理されているか（動的計算が必要な場合を除く）
- [ ] クラス命名規則が意味に基づいているか
    - [ ] テーマ: `.theme-*`
    - [ ] 機能: `.UpperCamelCase`
    - [ ] 質感: `.texture-*`
    - [ ] 状態: `.state-*`
    - [ ] 種別: `.lower-case`

## 6. モバイル/タブレットブラウザ対応 ([07.mobile_browser_rules.md](07.mobile_browser_rules.md))
- [ ] viewport meta に `width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no` を指定しているか
- [ ] ゲーム画面ルートで `100vh` だけに依存せず、`100dvh` を併用しているか
- [ ] ページ全体のブラウザスクロールを抑止し、必要なスクロールを内部スクロール領域に閉じ込めているか
- [ ] canvas / map / board などのゲーム操作領域に `touch-action: none` を指定しているか
- [ ] ブラウザ既定動作を抑止する pointer / touch / wheel listener を `{ passive: false }` で登録し、必要なタイミングで `preventDefault()` しているか
- [ ] iPad / iPhone Safari で操作対象になる領域に `user-select: none`, `-webkit-user-select: none`, `-webkit-touch-callout: none` を指定しているか
- [ ] safe area の影響を受ける固定UIでは `env(safe-area-inset-*)` を考慮しているか
- [ ] overlay / modal / tutorial mask が表示領域外にはみ出して操作不能にならないか
- [ ] レスポンシブ対応は寸法・配置・内部スクロールの調整を基本とし、比率維持のために scale を使う場合は、必要性・適用範囲と第6節の使用条件が明確か（UI 全体の拡縮も同じ条件で確認する）
- [ ] scale 使用時に、対応する画面サイズ・倍率で可読性・操作性を維持し、関連 UI・スクロール範囲・座標処理が表示と整合しているか
- [ ] 親子の拡縮や演出による倍率の重複、各機能での独自補正、固定倍率への依存がないか
- [ ] 音声を使用する場合、Safari 系の AudioContext とユーザージェスチャ起動を考慮しているか

## 7. 共通ライブラリ ([90.common_library.md](90.common_library.md))
- [ ] 共通ライブラリをローカル GameWorks OAK の `src/lib/` から相対 import しているか
- [ ] リモート build 時に GameWorks OAK リポジトリを checkout / link し、相対 import が解決されるか
- [ ] ゲームのマージ着手前・push直前に所定6コマンドで共通側master・HEADとremoteの一致・src/libの未コミット／未追跡なしを確認したか
- [ ] 失敗は未確認として報告・解消を待ち、文書変更とライブラリ変更を区別し、合格時に別途承認を求めていないか
- [ ] ゲーム担当が共通側を変更せず、解消によりライブラリが変わった場合はゲームの全テスト・ビルドを再実行したか
- [ ] ライブラリで提供されている機能の独自重複実装を避けているか
